# Правила безопасной записи в amoCRM

Эти правила обязательны для любого кода, который изменяет данные amoCRM, включая будущие AI-функции.

1. **Только явные действия пользователя.** Запись начинается с нажатия «Сохранить», «Создать задачу», «Выполнить», «Добавить» или выбора этапа. Импорт встреч, транскрипции, сопоставление и синхронизация ничего не пишут в amoCRM.
2. **Один путь записи.** Renderer → `crm:write` (IPC с проверкой отправителя) → `CrmService.execute` → `validateCommand` → `performMutation`. В React нет HTTP-запросов; токены и куки не попадают в renderer.
3. **Белый список маршрутов** (`security.ts → writeEndpoint`): `PATCH /api/v4/{leads|contacts|companies}/{id}`, `POST /api/v4/tasks`, `PATCH /api/v4/tasks/{id}`, `POST /api/v4/{entity}/notes`, `PATCH /api/v4/{entity}/notes/{id}`. Никаких DELETE, массовых операций, воронок, полей, пользователей и настроек аккаунта. Параметры строки запроса в записи запрещены.
4. **Проверка до отправки.** Поле существует у этой сущности и поддерживается; значения списков взяты из определения поля; числа, даты, ссылки, телефоны и почта корректны; этап принадлежит воронке; тип задачи есть в аккаунте; тексты непустые и ограничены по длине; управляющие символы отклоняются. Сделка редактируется, только если текущий пользователь — её ответственный.
5. **Только изменённые ключи.** Запрос содержит только то, что пользователь изменил. Кэшированная запись целиком никогда не отправляется.
6. **Конфликты.** Перед записью запись читается заново. Если она изменилась после открытия карточки и хотя бы один редактируемый ключ отличается от значения, которое видел пользователь, запись не отправляется: статус `conflict`, кэш обновляется версией amoCRM, пользователь видит «Карточка изменилась в amoCRM.», «Обновить данные» и «Посмотреть изменения». Изменения других ключей безопасны и сохраняются.
7. **Без фиктивного успеха.** Интерфейс показывает «Сохраняем…», затем «Сохранено в amoCRM» только после ответа amoCRM и повторного чтения. Кэш обновляется данными, которые вернула amoCRM, а не содержимым запроса.
8. **Без дублей.** Кнопки блокируются на время отправки; повторный клик в хуке игнорируется; один `operationId` выполняется один раз (`crm_operations.id`); одновременная запись в одну запись запрещена; одинаковое создание задачи/примечания в течение 15 секунд считается повтором; в создании передаётся `request_id` и проверяется в ответе.
9. **Повторы запросов.** 429 повторяется с паузой (запрос не обработан). PATCH повторяется при 502/503/504, так как задаёт абсолютные значения. POST не повторяется никогда: при потерянном ответе TalkCRM ищет созданную задачу/примечание (тот же текст, срок, время создания) и только тогда считает операцию выполненной; иначе — `needs_refresh` и просьба обновить карточку перед повтором.
10. **Права.** 403 → «У вас нет прав на это изменение в amoCRM.», без повторов, кэш не меняется. 401 → «Сессия amoCRM закончилась. Подключите аккаунт снова.», подключение помечается отключённым. 400/422 → «amoCRM отклонила изменение. Проверьте значения полей.»
11. **Общий ограничитель и авторизация.** Запись идёт через тот же `Transport` (интервал 200 мс) и тот же `OAuthSession` с единственным обновлением токена, что и чтение. В режиме входа сотрудника запросы отправляются той же изолированной сессией браузера.
12. **Без очереди офлайн.** Без соединения изменения не сохраняются для отложенной отправки.
13. **Высокорисковые действия подтверждаются:** закрытие сделки (успех/отказ), возврат закрытой сделки в работу, снятие связи встречи. Обычные правки, примечания и задачи — без лишних окон.
14. **Удаления нет.** Сделки, контакты, компании, задачи и примечания amoCRM не удаляются из TalkCRM.
15. **Журнал аудита** `crm_operations`: id операции, тип сущности, id в amoCRM, тип действия, статус, отпечаток команды, список изменённых ключей (без значений), id результата, `updated_at` amoCRM, категория ошибки, пользователь, время. Тексты примечаний, токены и транскрипции в журнал не пишутся; HTTP-лог содержит только метод, путь, статус и длительность.
16. **Проверка на реальных данных** выполняется только на записи, которую пользователь явно назначил тестовой. Закрытие сделок проверяется тестами, а не на клиентах.
